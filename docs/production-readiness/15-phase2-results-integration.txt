CONFIRMED DEFECT AND BASELINE EVIDENCE
The original helper read results, tested for a missing summary, then inserted or
updated it with no ownership across requests. The unique SQL index
IX_CandidateExamSummaries_ExamId_CandidateId_Unique prevents duplicate rows, but
does not make this read/compute/write operation safe.

Actual SQL Server reproduction, not an in-memory database:
- First explicit refresh paused immediately before SaveChanges; an overlapping
  read-repair completed first. Releasing the first request threw DbUpdateException
  with the above duplicate-key index identified by SqlException.
- For an existing summary, the first request computed 85 while a concurrent
  regrade/refresh computed and persisted 95. Releasing the older request persisted
  85 over the newer aggregate. The regression asserted expected 95, actual 85.
- A reused context with tracked results returned 80 after another context had
  persisted 95, demonstrating why a lock alone does not fix EF identity-map state.
Initial five-test baseline: 3 passed, 2 failed. After strengthening the existing
summary race to dirty its score before the interleave, that targeted baseline
also failed with the documented 85-versus-95 overwrite.

IMPLEMENTATION
RefreshCandidateExamSummaryInternalAsync takes a ReadCommitted SQL transaction
and a parameterized UPDLOCK, ROWLOCK on the existing AspNetUsers candidate row
BEFORE reading results or the summary. This also owns first creation where there
is no summary row to lock. SaveChanges and transaction commit finish before the
next refresh for that candidate can read/compute its aggregate.

Aggregate results use AsNoTracking, so previously tracked regrading data cannot
replace newly read values. An existing tracked summary is reloaded under ownership,
refreshing its original-value snapshot as well as current fields. The summary DTO
reads the best result's score denominator explicitly, preserving percentage
calculation without relying on tracking-driven navigation fixup.

Preserved rules: non-deleted results only; published and unpublished results both
count; highest score wins with earliest FinalizedAt breaking score ties; latest
uses descending FinalizedAt, not StartedAt or attempt number; LastAttemptAt uses
the selected latest attempt's StartedAt; pass flags, attempt counts, remaining
attempt calculation, creation audit, and no-results behavior remain intact.
No certificate generation or publishing semantics were changed.

LIMITS AND PRODUCT DECISIONS
This is backend service/SQL validation, not HTTP/browser, realistic exam load,
migration rollout, or whole-system acceptance. The lock serializes refreshes for
one candidate across exams; it is not a process-local mutex. Final result writes
still commit before summary refresh, preserving the existing integration boundary;
this is not a new atomic transaction covering grading and summary creation.

Single-result publication automatically creates a certificate for passed results;
bulk/exam publication does not. That difference remains for product review, not
an inferred defect to change in this patch. CacheService is a no-op; missing
certificate cache invalidation is not a live bug.
