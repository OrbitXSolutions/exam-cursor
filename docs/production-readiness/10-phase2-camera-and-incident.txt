FINDINGS — IMPORTANT DISTINCTION
An initial investigation identified a create-incident handler that navigated
away and would dispose the viewer. Parent verification found it was UNUSED:
handleCreateIncident had exactly one occurrence, its declaration, and no JSX
action binding. That dormant code is NOT proof of the reported customer's
reachable backup failure. The current live page has no bound create-incident
backup action. No new optional backup UI was introduced or re-enabled.

A separate, reachable camera-display defect was confirmed in source:
- handleReviewIncident, handleAddTime, and handleToggleFlag call loadSession.
- loadSession previously set the page-wide loading flag on every refresh.
- The loading render returns only a spinner, removing the live video elements.
- The viewer effect depends on attemptId and session status, not loading. For
  the same active session it need not reconnect or receive another stream event.
- Webcam srcObject was assigned on stream arrival. Remounting a fresh video
  element after the spinner therefore loses its binding to the existing stream.
- A failed follow-up fetch also redirected away, invoking viewer cleanup even
  though a nonessential refresh failure does not establish exam termination.
This is a confirmed component lifecycle risk, not a real-browser reproduction.

CHANGES MADE / WHY
The existing loader now distinguishes an action refresh from initial load:
- Initial loading/error navigation behavior remains unchanged.
- Incident-review, flag and add-time refreshes keep the video DOM mounted.
- Refresh failure retains monitoring and shows the existing error toast rather
  than redirecting the proctor. A confirmed non-active session still follows
  the existing termination/end behavior.
- Removed only the unused optional create-incident handler and its import,
  keeping the already-unavailable shortcut from being accidentally rebound.
  Incident APIs and other incident management pages are unchanged.
- No changes to webcam acquisition, MediaStream ownership, WebRTC peer setup,
  screen capture, candidate recording, codecs or viewer disconnection logic.
  The actual WebRTC effect body and dependency list are unchanged.
