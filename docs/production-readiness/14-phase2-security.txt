Refresh and deactivation
- Refresh requires an existing, active, unblocked, undeleted user, a nonempty
  matching refresh token, and an explicitly present future expiry.
- Successful refresh still rotates access and refresh tokens. Failed Identity
  persistence does not return a successful token response.
- Deactivation clears both refresh credential fields in the same Identity update,
  checks persistence success, and does not restore credentials on reactivation.
- This does NOT instantly revoke already-issued JWTs. Their normal expiry and
  existing authentication configuration still apply. No authentication redesign.

ProctorHub authorization
- Candidate access is exact attempt ownership, not general exam access.
  A sibling candidate assigned to the same exam cannot join the other attempt.
- Monitoring requires Proctor/Admin plus the existing department OR nondeleted
  explicit ExamProctor assignment entitlement, or SuperAdmin.
- Missing/deleted attempts and deleted exams cannot be joined.
- Both room joins validate the client role against the server-derived role.
- Every media/signaling/control invocation requires a prior authorized join to
  its channel and rechecks current caller ownership/monitor entitlement.
  Publisher-only and monitor-only operations enforce their respective roles.
- Follow-up: when an invocation or join detects entitlement loss, all main and
  screen memberships for that attempt are removed before denying the caller.
  This includes role/connection-specific groups; a removal failure aborts the
  connection. Wrong-channel/wrong-operation-role calls cannot bypass this check.
- Directed answers/ICE use SignalR groups partitioned by attempt, media channel,
  validated peer role, and connection ID. Wrong/unknown recipients receive
  nothing; empty required answer targets fail. No arbitrary Clients.Client send
  remains in the hub and there is no process-local recipient registry.
- Context.Items records only this connection's own authorized room role.
  Distributed delivery and recipient membership are managed by SignalR/Redis.
  Leave removes all relevant subgroups; disconnect cleanup is SignalR-owned.
  Partial join/leave failures abort the connection rather than retaining a
  partially authorized receive-only connection.
- Main attempt groups remain for existing backend notifications. Offers, ICE,
  peer lifecycle, and directional controls go to the appropriate peer role.

Frontend compatibility checked
- proctor-signaling.ts connect() joins the main room. connectScreenRoom() calls
  connect() first, then joins screen; reconnect rejoins both when appropriate.
- Candidate/proctor webcam and screen offer/answer/ICE sequences remain supported.
- Screen status intentionally requires the main-room candidate join and reaches
  main-room monitors, matching screen-share-publisher.ts and current viewers.
- Leaving screen does not remove camera/main membership. Reconnected connections
  must join again. A single authorized connection may legitimately join both.

The seven tests exercise:
1. Refresh rejection for inactive/pending/suspended/blocked/deleted/missing users,
   invalid access tokens, missing/expired expiry, absent/empty/mismatched refresh
   tokens; active rotation, old-token replay denial, persisted replacement.
2. Persisted deactivation credential removal, rejection before/after reactivation,
   and the explicitly unchanged cryptographic validity of an existing JWT.
3. Real SQL Identity concurrency failures during refresh and deactivation:
   failure responses and unchanged persisted credentials/status.
4. Real authenticated hub rejection of unjoined callers (including otherwise
   entitled users), sibling candidates, cross-department Proctor/Admin, spoofed
   roles, candidate control escalation, monitor publisher impersonation, and
   unauthenticated negotiation.
5. Working same-department Proctor/Admin, cross-department explicitly assigned
   proctor, assigned proctor without department, and SuperAdmin flows across two
   independent Redis-backed Kestrel nodes; webcam/screen negotiation, targeted
   and broadcast ICE, controls, statuses, and leave notifications.
6. Wrong attempt/media/role/self/unknown/empty targets; camera/screen separation;
   targeting a peer after leave; disconnected IDs versus replacement connections;
   reconnect requiring an authorized rejoin.
7. The final executed revocation regression: an idle revoked monitor first
   demonstrably receives an offer, then its rejected publisher-only invocation
   removes BOTH channels without any Leave/disconnect. Later broadcasts, directed
   ICE, and backend base-group messages do not reach that still-connected peer.
   Other revoked operations/joins and deleted/missing attempts are rejected.
