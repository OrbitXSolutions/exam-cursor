PRODUCTION CHANGES
1. StartAttemptAsync and StartExamAsync acquire an update lock on the existing
   AspNetUsers candidate row in an explicit READ COMMITTED transaction before
   checking the attempt range/count. This provides a lock even for the first
   attempt, without SERIALIZABLE shared-range-to-insert conversion deadlocks.
   Both entry points use the same candidate row. Different candidates do not
   deliberately share this lock; starts for one candidate across different
   exams are serialized. An existing active attempt is also read with UPDLOCK.
   Schedule time is evaluated after acquiring the candidate lock.

2. Single save, bulk save, Candidate save, and both submit implementations
   acquire UPDLOCK, ROWLOCK on the attempt before reading its mutable status
   and answers. The transaction lasts through the associated writes. Waiting
   saves therefore see the prior save's answer row instead of both inserting;
   a save that wins completes before submission; a submit that wins causes
   subsequent saves to observe the terminal status.

3. Submission's ExecuteUpdate and subsequent event/session SaveChanges now
   participate in the same transaction. SQL failure inserting the event does
   not leave the attempt irreversibly Submitted without its event/session
   update. Successful commits precede existing SignalR/background-grading
   dispatch and cache invalidation. This is not a durable outbox guarantee.

4. Expiry/disconnect paths that intentionally save an expired state commit that
   state even though the answer/start response is a business-rule rejection.
   Disconnect-helper invalidation is deferred until commit in transactional
   answer paths; its existing nontransactional callers retain their behavior.

5. Existing SQL uniqueness constraints remain the integrity backstop:
   Attempts(ExamId, CandidateId, AttemptNumber) and
   AttemptAnswers(AttemptId, QuestionId). No constraint was removed or weakened.

BUSINESS-RULE BOUNDARY
The existing APIs are deliberately not unified:
- AttemptService rejects late submission and duplicate submission.
- CandidateService accepts a time-expired-but-not-yet-marked-Expired attempt's
  submission, and returns success for an already submitted attempt.
- CandidateService retains admin overrides, Resumed links, fixed/flexible
  schedule handling and question-builder behavior.
- Existing answer validation, ownership checks, maximum attempts and disconnect
  thresholds were not replaced with new policies.

Real SQL tests cover ownership/invalid answers, timer expiry, disconnect expiry,
maximum-attempt rejection, Candidate late/duplicate submission, and concurrent
consumption of exactly one admin override. They also preserve complete snapshot
rollback and the already-atomic SaveChanges answer rollback.
Fixed-start grace windows, access-code permutations, shuffled/builder question
selection and every lifecycle status permutation were not exhaustively tested.

BACKEND-ONLY 50-CANDIDATE WORKLOAD
Definition:
- Fifty independent candidate identities, one exam, ten essay questions each.
- A common release starts fifty candidate pipelines. Each pipeline starts an
  attempt, overlaps two ten-answer bulk saves, then submits.
- Counts per run: 50 starts + 100 bulk saves + 50 submits = 200 service operations.
- Phases overlap across candidates; this is not a barrier-synchronized burst
  of fifty simultaneous submissions.
- Workload start calls use AttemptService. CandidateService mixed-entry-point
  correctness is tested separately, not claimed as a 50-client Candidate load run.
- Stopwatch excludes database creation/seeding and final verification.
- All operation results must succeed. Independent verification requires:
  50 Submitted attempts; 500 question snapshots; 500 unique answer rows;
  1,000 AnswerSaved events; 50 Started events; 50 Submitted events;
  50 completed proctor-session records.

LIMITATIONS AND REQUIRED CUSTOMER ACCEPTANCE
- These are service-to-SQL tests with separate DbContexts, not HTTP tests or two
  deployed application nodes. SignalR is a no-op test hub; Candidate background
  grading is deliberately excluded by a test scope factory. No Redis transport,
  browser, camera, WebRTC, media upload, notification receipt or grading/result
  completion was measured. In particular, this is NOT evidence of 50 live cameras.
- This workload does not establish an SLA, a maximum user count, sustained
  throughput, long-duration stability, or acceptable worst-case tail latency.
  Several start calls took multiple seconds; acceptance thresholds must be
  agreed with the system owner rather than inferred from "tests passed".
- The tested transactions assume the application's current SQL Server provider
  and request-scoped DbContext pattern. Retry after injected failure uses a
  fresh context. No retrying EF execution strategy, general deadlock retry,
  context-reuse contract or lock-timeout policy was introduced.
- Timer/session getters, proctor/admin control writers, expiry workers and
  other lifecycle paths were not exhaustively interleaved in this bounded
  suite. This report does not claim all possible lifecycle races are removed.
- Late Candidate submission retains its existing special behavior, including
  the distinct session-handling branch. Broader lifecycle-policy reconciliation
  is a separate decision, not silently included in this concurrency patch.
- No production index execution plans, SQL wait statistics, CPU/GC/memory,
  connection-pool saturation, packet loss, node failure or storage exhaustion
  were measured. ROWLOCK is a requested SQL lock granularity, not proof that
  escalation or unrelated database deadlocks can never occur.
- Customer acceptance still requires representative exams, all configured
  monitoring/media features, two actual application nodes and shared services,
  simultaneous start/save/submit traffic, reconnection/node-loss drills,
  persisted-state inspection, and measured resource/error/latency thresholds.
