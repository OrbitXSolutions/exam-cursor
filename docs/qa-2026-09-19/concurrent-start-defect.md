This is a confirmed application concurrency failure during a simulated ordinary workload. The API process remained alive. Full50-active status was never reached, so the failed ramp does not establish sustained50-candidate capacity.

Minimal source fix in `Backend-API/Infrastructure/Services/Candidate/CandidateService.cs` and `Backend-API/Infrastructure/Services/Attempt/AttemptService.cs`: retain the shared per-candidate parent-row lock and ReadCommitted transaction; resolve the candidate's active attempt ID with a normal query; if present, acquire the existing UPDLOCK/ROWLOCK only through its primary key and recheck active status before resuming. The former composite update-lock scan can retain locks beyond the intended row depending on its execution plan; that mechanism is an inference from the failing query and SQL1205 logs, not a captured deadlock graph. Narrowing the lock target also avoids needing a lock scan for first attempts. Max-attempt/override checks and atomic creation remain inside the same transaction. No schema/index/isolation-level change, retry suppression, limiter change or business-policy change was introduced.
