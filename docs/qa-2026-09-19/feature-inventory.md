## Concrete variants and rules found in current code

### Question/scoring variants

- Seeded types (`QuestionTypeConfiguration` and frontend question renderer): `1 MCQ_Single`, `2 MCQ_Multi`, `3 TrueFalse`, `4 Subjective`. Subjective replaces legacy ShortAnswer/Essay/Numeric in the UI. Do not claim Numeric tolerance or legacy ShortAnswer as exercised unless explicitly arranged and tested; answer-key DTO fields alone do not prove an exposed supported workflow.
- `GradingService.GradeMcqAnswer`: single/TrueFalse uses exact equality of selected and correct option sets. Empty selection earns zero.
- MCQ multi explicit option points: sum **correct selected** option points, cap to the attempt question maximum; incorrect selections contribute zero. `IsCorrect` is true when awarded score equals max.
- MCQ multi legacy absent option points: distribute maximum equally over correct options; wrong selections add zero penalty. `IsCorrect` uses exact selected/correct set equality, so selecting every option can earn full numeric points while `IsCorrect=false`. This is existing code behavior; treat any policy change as a business decision unless requirements establish otherwise.
- Create-question validator requires bilingual body, positive points ≤1000, subject, valid difficulty, and nonnegative option points summing to question points when type=2 has explicit points. Probe whether incorrect options can hold positive points and whether update/bulk paths preserve the same invariants.
- Legacy short-answer grader combines English/Arabic accepted JSON answers, optional trim/whitespace normalization/case sensitivity; Numeric is not auto-graded by the current grader. Subjective goes manual.
- Attempt question points determine maximum; pass rule is `TotalScore >= Exam.PassScore` (**absolute points**, not percent). Display percentage is separate.
- Important snapshot probe: grading reads current question/option data along with attempt question points. Check behavior if an author edits/deletes keys/options after candidate start/finish before grading.

### Exam variations

- `ExamType`: Flex=0, Fixed=1. DTO describes fixed as shared start/end, but `CandidateService.StartExamAsync` applies a start grace window while its expiry assignment is `min(now + DurationMinutes, EndAt)`. Generic `AttemptService.StartAttemptAsync` applies start/end boundaries but lacks the fixed grace check in inspected flow. Compare concrete runtime behavior before filing a defect.
- MaxAttempts=0 means unlimited. Duration allowed 1–600 minutes; StartAt/EndAt optional but EndAt must be later if both supplied. Past/future and timezone display need browser verification.
- Static sections can have topics, manual or random bank selection, per-exam question updates/order. Builder uses Subject=1 or Topic=2 source with pick count, section duration, order and optional pass score. Compare selected pool size, excluded inactive/deleted questions, generated attempt uniqueness/order and score estimate versus real picked total.
- Result flags: `ShowResults`, `AllowReview`, `ShowCorrectAnswers` (settings DTO documents requiring review for correct answers).
- Proctor flags: `RequireProctoring`, `RequireIdVerification`, `RequireWebcam`, `EnableScreenMonitoring`, ScreenMonitoringMode `Disabled/Optional/Required/Strict`, grace seconds (default 20).
- Integrity flags: `PreventCopyPaste`, `PreventScreenCapture`, `RequireFullscreen`, `BrowserLockdown`, `MaxViolationWarnings` (0 disables auto-termination).
- Access policy: `IsPublic`, `RestrictToAssignedCandidates`, `AccessCode`, `IsWalkIn`. Walk-in custom fields are Text=1/Number=2 with required/optional and bilingual label/order. Share link has active/expiration/revocation state and may issue candidate access/refresh tokens via candidate selection or registration.

### Lifecycle/state rules to verify

- Attempt statuses: Started=1, InProgress=2, Submitted=3, Expired=4, Cancelled=5, Paused=6, ForceSubmitted=7, Terminated=8, Resumed=9. Expiry reasons: None=0, active timer=1, disconnected timer=2, exam window=3, disconnect budget=4.
- Grading: Pending=1, AutoGraded=2, ManualRequired=3, Completed=4. Result finalization and publication are separate. Candidate-service submission triggers background grading; inspect actual eventual state and failure behavior.
- Proctor session: Active=1, Completed=2, Cancelled=3; mode Soft=1/Advanced=2. Identity: Pending=0/Approved=1/Rejected=2/Flagged=3. Liveness: NotChecked/Passed/Failed/Inconclusive.
- Incident: Open→InReview→Resolved→Closed with reopen, assignment/reassignment, evidence linking, comments, decision and timeline; outcomes Cleared/Suspicious/Invalidated/Escalated. Appeal enum exists, but no appeal endpoint found in inspected Incident controller—do not claim user-facing appeal coverage based on enum alone.

## High-priority probes derived from implementation, not confirmed findings

2. Compare candidate result/review, Grading/my-result, ExamResult/my-result/my-summary and my-results for publication/ShowResults/ShowCorrectAnswers consistency.
3. Verify exports physically download: `ExamResultService.ProcessPendingExportJobsAsync` currently contains a TODO and sets placeholder Completed/FilePath without generating file. Its scheduling also needs runtime confirmation.
4. Verify safe author edits across active/past attempts and grading snapshots; duplicate start/submit/manual-grade/finalize races.
5. ResourceAuthorizationService gives department staff exam scope and explicitly assigned proctors cross-department scope; candidate-only actor may access assigned or previously attempted exam. Controllers still need role restrictions. Candidate own-resource helpers must not become peer-attempt access through exam grants.
6. Public share selection intentionally accepts candidate ID and issues tokens. Determine whether possession of link is intended sufficient proof of identity; ensure token scope cannot escape the exam. Do not silently redesign this business rule.
7. Inspect underlying media integration even if camera/screen permissions are unavailable; label physical/browser/simulated evidence separately.
